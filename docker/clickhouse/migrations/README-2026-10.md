# Prod runbook — October 2026 OTEL ingestion migration

Three changes, in this order. Each step says how to verify it and how to undo it.
Nothing here has been run against prod; the agent that wrote it had no
ClickHouse to test against, so **do step 0 first** and read each verification
query's output before moving on.

**Server:** `clawdgg` (46.224.85.32) · **Compose file:** `/opt/clawdgg/docker-compose.staging.yml`

Shorthand used below — define it once per shell:

```bash
CH="ssh clawdgg docker compose -f /opt/clawdgg/docker-compose.staging.yml exec -T clickhouse clickhouse-client"
```

---

## 0. Back up first

`EXCHANGE`/`RENAME` is cheap to reverse, but a bad `INSERT ... SELECT` is not,
and the daily_stats import is not reversible at all. Take both:

```bash
# a) ClickHouse native backup of the two raw tables (fastest to restore)
$CH --query "BACKUP TABLE clawd.metrics_raw, clawd.events_raw TO Disk('backups', 'pre_2026_10.zip')"

# If no `backups` disk is configured, dump instead — slower but needs no setup:
$CH --query "SELECT * FROM clawd.metrics_raw FORMAT Native" > metrics_raw.$(date +%F).native
$CH --query "SELECT * FROM clawd.events_raw  FORMAT Native" > events_raw.$(date +%F).native

# b) The SQLite users/daily_stats DB, which the step-3 import reads
ssh clawdgg 'docker compose -f /opt/clawdgg/docker-compose.staging.yml \
  exec -T app sqlite3 /app/data/clawd.db ".backup /app/data/clawd.pre_2026_10.db"'
```

Record the baseline numbers. Every later step is checked against these:

```bash
$CH --multiquery --query "
USE clawd;
SELECT 'metrics raw'    AS k, count() AS v FROM metrics_raw
UNION ALL SELECT 'metrics final',  count() FROM metrics_raw FINAL
UNION ALL SELECT 'events raw',     count() FROM events_raw
UNION ALL SELECT 'events final',   count() FROM events_raw FINAL
UNION ALL SELECT 'prompts',        count() FROM events_raw FINAL WHERE event_name = 'claude_code.user_prompt'
UNION ALL SELECT 'tokens',         toUInt64(sum(value)) FROM metrics_raw FINAL WHERE metric_name = 'claude_code.token.usage'
UNION ALL SELECT 'cost cents',     toUInt64(sum(value) * 100) FROM metrics_raw FINAL WHERE metric_name = 'claude_code.cost.usage'
FORMAT PrettyCompact"
```

## 2. Re-key the raw tables (`row_id`)

`2026-10-18_dedup_identity_v2.sql`. **Order matters: this runs BEFORE the app is
deployed.** The new app writes a `row_id` column; against the old tables every
insert fails on an unknown column. The old app writing to the new tables is
fine — `row_id` defaults to `''`.

### 2a. Create and fill the v2 tables

The file applies steps 1–2 (create + copy) and stops; the swap statements at the
bottom are commented out on purpose.

```bash
$CH --multiquery < docker/clickhouse/migrations/2026-10-18_dedup_identity_v2.sql
```

The copy reads the live tables without `FINAL` and without locking them, so the
app can stay up. Any rows that arrive during the copy are picked up by the catch-up
in 2c.

### 2b. Verify the copy

```bash
$CH --multiquery --query "
USE clawd;
SELECT 'metrics raw old' AS k, count() AS v FROM metrics_raw
UNION ALL SELECT 'metrics raw new',   count() FROM metrics_raw_v2
UNION ALL SELECT 'metrics no hash',   countIf(row_id = '') FROM metrics_raw_v2
UNION ALL SELECT 'metrics final old', count() FROM metrics_raw FINAL
UNION ALL SELECT 'metrics final new', count() FROM metrics_raw_v2 FINAL
UNION ALL SELECT 'events raw old',    count() FROM events_raw
UNION ALL SELECT 'events raw new',    count() FROM events_raw_v2
UNION ALL SELECT 'events no hash',    countIf(row_id = '') FROM events_raw_v2
UNION ALL SELECT 'events final old',  count() FROM events_raw FINAL
UNION ALL SELECT 'events final new',  count() FROM events_raw_v2 FINAL
FORMAT PrettyCompact"
```

Required:

| Check | Expected |
|---|---|
| `raw new` vs `raw old` | equal, or `new` slightly higher if rows landed during the copy |
| `no hash` | **0** on both |
| `final new` vs `final old` | `new` **>=** `old`. Higher means previously-collapsed rows came back. **Lower is a bug — stop and do not swap.** |

And the headline totals, which must not fall:

```bash
$CH --multiquery --query "
USE clawd;
SELECT 'tokens old' AS k, toUInt64(sum(value)) AS v FROM metrics_raw     FINAL WHERE metric_name = 'claude_code.token.usage'
UNION ALL SELECT 'tokens new',  toUInt64(sum(value)) FROM metrics_raw_v2 FINAL WHERE metric_name = 'claude_code.token.usage'
UNION ALL SELECT 'prompts old', count() FROM events_raw     FINAL WHERE event_name = 'claude_code.user_prompt'
UNION ALL SELECT 'prompts new', count() FROM events_raw_v2  FINAL WHERE event_name = 'claude_code.user_prompt'
FORMAT PrettyCompact"
```

Confirm the SQL hash and the app's hash agree — if they do not, every historical
row is orphaned and OTLP retries stop deduplicating. Take one real row and
re-hash it locally:

```bash
$CH --query "SELECT toString(timestamp), user_id, session_id, metric_name, model,
  token_type, line_type, tool, decision, language, source, query_source, speed,
  effort, agent_name, skill_name, plugin_name, mcp_server_name, mcp_tool_name,
  start_type, terminal_type, app_version, account_uuid, organization_id,
  provenance, row_id FROM clawd.metrics_raw_v2 LIMIT 1 FORMAT JSONEachRow"
```

Paste the values into the local repo and compare:

```bash
bun -e 'const {metricRowId}=await import("./src/db/clickhouse.ts");
  console.log(metricRowId({ /* the fields above, minus row_id */ }))'
```

It must print the `row_id` ClickHouse computed. (`METRIC_IDENTITY_COLUMNS` in
`src/db/clickhouse.ts` lists the fields in hash order; the digest is also
reproducible with `shasum -a 256` over the values joined by `\x1f`, truncated to
32 hex chars.)

### 2c. Swap, then deploy

Stop the app so no insert is lost between the catch-up and the rename:

```bash
ssh clawdgg 'cd /opt/clawdgg && docker compose -f docker-compose.staging.yml stop app'
```

Copy anything that arrived during 2a–2b (the v2 key dedups the overlap, so
re-copying rows already present is harmless):

```bash
# Re-run just the two INSERT ... SELECT statements from the migration file.
sed -n '/^INSERT INTO metrics_raw_v2/,/^FROM metrics_raw;/p' \
  docker/clickhouse/migrations/2026-10-18_dedup_identity_v2.sql | $CH --multiquery --query "USE clawd; $(cat)"
```

If that pipe feels fragile, simplest alternative: re-run the whole file —
`CREATE TABLE IF NOT EXISTS` is a no-op and the inserts just re-copy.

Swap (atomic, one statement per table):

```bash
$CH --multiquery --query "
USE clawd;
RENAME TABLE metrics_raw TO metrics_raw_old_2026_10, metrics_raw_v2 TO metrics_raw;
RENAME TABLE events_raw  TO events_raw_old_2026_10,  events_raw_v2  TO events_raw;"
```

Confirm the shape, then deploy the app:

```bash
$CH --query "SELECT name, sorting_key FROM system.tables
  WHERE database = 'clawd' AND name IN ('metrics_raw','events_raw') FORMAT Vertical"
# both sorting keys must end in `row_id`

rsync -avz src/ clawdgg:/opt/clawdgg/src/ && ssh clawdgg 'cd /opt/clawdgg && \
  docker compose -f docker-compose.staging.yml up -d --build app'
```

Post-deploy smoke test — run Claude Code locally for a minute, then:

```bash
$CH --query "SELECT metric_name, query_source, count() FROM clawd.metrics_raw
  WHERE timestamp > now() - INTERVAL 10 MINUTE
  GROUP BY metric_name, query_source ORDER BY count() DESC FORMAT PrettyCompact"
```

Expect non-empty `query_source` on `token.usage` / `cost.usage` rows and no
empty `row_id`:

```bash
$CH --query "SELECT countIf(row_id = '') FROM clawd.metrics_raw WHERE timestamp > now() - INTERVAL 10 MINUTE"
```

Also check the app log is clean — a gzip batch now returns 200 instead of 500,
and a bad payload logs `[OTel] Rejected ...` rather than retrying forever:

```bash
ssh clawdgg 'docker compose -f /opt/clawdgg/docker-compose.staging.yml logs --tail=200 app' | grep -i otel
```

### 2d. Rollback

```bash
ssh clawdgg 'cd /opt/clawdgg && docker compose -f docker-compose.staging.yml stop app'
$CH --multiquery --query "
USE clawd;
RENAME TABLE metrics_raw TO metrics_raw_v2, metrics_raw_old_2026_10 TO metrics_raw;
RENAME TABLE events_raw  TO events_raw_v2,  events_raw_old_2026_10  TO events_raw;"
# then redeploy the previous image, which does not write row_id
ssh clawdgg 'cd /opt/clawdgg && docker tag clawdgg-app:<previous-tag> clawdgg-app:latest \
  && docker compose -f docker-compose.staging.yml up -d app'
```

Rows written to the v2 tables after the swap stay in `*_v2` and can be copied
forward later. Keep `*_old_2026_10` for at least two weeks of clean running;
drop only then:

```bash
$CH --multiquery --query "USE clawd; DROP TABLE metrics_raw_old_2026_10; DROP TABLE events_raw_old_2026_10;"
```

## 3. Import pre-OTEL `daily_stats` into ClickHouse

> **Do not run `--apply` until the legacy read paths are gone.** Two of them
> still serve the same history:
>
> - `src/routes/api.ts` adds `users.legacy_total_*` to the ClickHouse totals for
>   all-time views (the `legacyPrompts` / `legacyCost` / `legacyLines` /
>   `legacyCommits` selects, and the sync that writes `users.total_*` from them).
> - `clickhouse.getLegacyChartData` reads SQLite `daily_stats` directly, and its
>   `date <= otelSetupDate` is the boundary double-count the strict `<` in this
>   import fixes.
>
> With both live **and** this import applied, every all-time total doubles.
> Those files are owned by another track; the import stays dry-run until they
> land.

Dry run — safe any time, writes nothing:

```bash
ssh clawdgg 'cd /opt/clawdgg && docker compose -f docker-compose.staging.yml \
  exec -T app bun docker/clickhouse/migrations/2026-10-18_import_daily_stats.ts'
```

Read the summary: days, prompts, tool calls, tokens and cost per user, and the
row counts it would write. Check the day range ends the day **before** each
user's `otel_setup_date`.

Apply:

```bash
ssh clawdgg 'cd /opt/clawdgg && docker compose -f docker-compose.staging.yml \
  exec -T app bun docker/clickhouse/migrations/2026-10-18_import_daily_stats.ts --apply'
```

**Verify** — the imported rows reproduce the SQLite numbers:

```bash
$CH --query "
SELECT user_id,
       count(DISTINCT toDate(timestamp)) AS days,
       countIf(event_name = 'claude_code.user_prompt') AS prompts,
       countIf(event_name = 'claude_code.tool_result') AS tool_calls,
       min(toDate(timestamp)) AS first_day, max(toDate(timestamp)) AS last_day
FROM clawd.events_raw FINAL WHERE provenance = 'legacy'
GROUP BY user_id FORMAT PrettyCompact"

$CH --query "
SELECT user_id,
       toUInt64(sumIf(value, metric_name = 'claude_code.token.usage')) AS tokens,
       round(sumIf(value, metric_name = 'claude_code.cost.usage'), 2) AS cost_usd,
       toUInt64(sumIf(value, metric_name = 'claude_code.commit.count')) AS commits
FROM clawd.metrics_raw FINAL WHERE provenance = 'legacy'
GROUP BY user_id FORMAT PrettyCompact"
```

Compare against SQLite for the same window:

```bash
ssh clawdgg 'docker compose -f /opt/clawdgg/docker-compose.staging.yml exec -T app \
  sqlite3 /app/data/clawd.db "SELECT d.user_id, count(*), sum(d.prompt_count), sum(d.tool_call_count),
    sum(d.input_tokens + d.output_tokens + d.cache_read_tokens + d.cache_creation_tokens),
    sum(d.cost_usd_cents)/100.0
  FROM daily_stats d JOIN users u ON u.id = d.user_id
  WHERE u.otel_setup_date IS NOT NULL AND d.date < u.otel_setup_date
  GROUP BY d.user_id;"'
```

Every column must match. Re-run the dry run afterwards: it must report
`0 new days` — that is the idempotency check.

**Rollback:**

```bash
$CH --multiquery --query "
USE clawd;
ALTER TABLE metrics_raw DELETE WHERE provenance = 'legacy';
ALTER TABLE events_raw  DELETE WHERE provenance = 'legacy';"
```

`ALTER ... DELETE` is a mutation, not instant — watch it finish:

```bash
$CH --query "SELECT table, is_done, latest_fail_reason FROM system.mutations
  WHERE database = 'clawd' AND NOT is_done FORMAT Vertical"
```

`provenance='legacy'` is set on every imported row and on nothing else, so this
removes exactly what the import added.

## Known limits after all three steps

- **Already-collapsed rows are gone.** Step 2 stops the collapsing; it cannot
  recover what ClickHouse already merged away. Figures for the period before
  the swap remain an undercount wherever two datapoints shared the old key.
- **Legacy days have no detail.** The import reconstructs counts and sums, not
  events: `prompt_length` is 0, `model` and `session_id` are empty, and every
  row sits at 12:00 UTC (so the activity heatmap shows a noon spike on legacy
  days, and `getUserDailyMetrics.sessions`, which is `uniqExact(session_id)`,
  reads 1 per legacy day — the true count is in the `claude_code.session.count`
  metric row. Switching that query to sum the metric is a separate call, worth
  making when the legacy read paths are retired.)
- **Haiku 5.5 long prompts under-report cost.** It is priced by prompt length
  (5x above 100K input tokens) and nothing in the OTEL stream or the JSONL
  carries the length that decides it, so `src/lib/pricing.ts` uses the standard
  tier.
- **`agent_id` / `parent_agent_id` and a 5m/1h cache-creation split are not
  captured** because the current docs do not define them. Subagent attribution
  is `query_source` + `agent.name`; `api_request` reports one
  `cache_creation_tokens` with no TTL breakdown.
