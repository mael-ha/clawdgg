# Prod runbook — October 2026 OTEL ingestion migration

Seven steps, in this order. Each says how to verify it and how to undo it.

Step 0b is **already done on prod** (2026-10-18). Step 6 is the one that puts
the lost tokens back — read "Why there is anything to recover" before running
anything, because 63% of the live token total is currently missing and that
changes every dollar figure on the site.

**The app stays up for all of them.** That is not a convenience — it is the
whole design. The OTel SDK *drops* a batch it cannot deliver, and Claude Code's
metrics use delta temporality, so a batch refused during a maintenance window
is **gone, not resent**. Any step that stops the app loses exactly the data
this migration exists to protect. `EXCHANGE TABLES` is what makes that possible.

**Server:** `clawdgg` (46.224.85.32) · **Compose file (on the server, not in
this repo):** `/opt/clawdgg/docker-compose.staging.yml`

Shorthand — define both once per shell:

```bash
COMPOSE=/opt/clawdgg/docker-compose.staging.yml
CH="ssh clawdgg docker compose -f $COMPOSE exec -T clickhouse clickhouse-client"
```

Every `docker compose` command below takes the compose file from `$COMPOSE`, so
if the prod file is ever renamed, change it in one place.

## What has been verified, and how

Unlike the previous version of this runbook, the identity hash is no longer
asserted on reasoning alone.

`docker/clickhouse/migrations/identity-parity.test.ts` inserts 15 rows through
the **real** serialisation path (the JSONEachRow body `src/db/clickhouse.ts`
sends) into the **real** DDL, and asserts ClickHouse's own expression
recomputes the row_id TypeScript computed — over empty strings, column
defaults, CJK and Greek text, a surrogate pair split at a truncation boundary,
`provenance` values other than the default, millisecond edges, and
`event_sequence` at `Number.MAX_SAFE_INTEGER`. Run it before trusting step 3:

```bash
cd /path/to/clawdgg
curl https://clickhouse.com/ | sh          # ~182 MiB standalone binary, no server
CLICKHOUSE_BIN=./clickhouse bun test docker/clickhouse/migrations
```

Two things that test established, both of which shaped the steps below:

1. **`input_format_skip_unknown_fields` defaults to `1`.** A JSON body naming a
   column the table does not have is **silently accepted and the value
   dropped**. The old claim that "the insert fails loudly on an unknown column"
   is false, so the column-ordering in step 1 cannot be enforced by waiting for
   an error — step 2 verifies the columns **positively** before deploying, and
   step 2's post-deploy check looks for a non-empty `row_id` rather than for an
   absent exception.
2. **A lone surrogate rejects the whole batch.** `JSON.stringify` of a string
   truncated mid-emoji emits a bare `\ud83d`, and ClickHouse answers
   `CANNOT_PARSE_ESCAPE_SEQUENCE` for the **entire** insert. `insert()` now
   replaces unpaired surrogates with U+FFFD, which is what Node's UTF-8
   encoding does anyway — so the row_id is unchanged by it.

### 0b. Remove the TTLs — do this BEFORE the copy

> **DONE on prod, 2026-10-18 16:05 UTC.** `metrics_raw` had its TTL removed;
> `events_raw` **never had one** and answered `Table doesn't have any table TTL
> expression`. Both verified clear afterwards, at 564,972 and 1,477,211 rows.
> Re-read 0b only if you are migrating a different instance.

The schema says both raw tables carry `TTL toDateTime(timestamp) + INTERVAL 365
DAY`, which silently deletes a user's first year the moment it turns 366 days
old — the opposite of what the daily_stats import is for. The v2 tables have no
TTL, and the OLD tables must lose theirs too, or rows can expire out from under
the copy between step 3 and step 4.

**ASK BEFORE REMOVING.** `REMOVE TTL` on a table that has none is NOT a no-op:
it raises `Table doesn't have any table TTL expression`, which in a
`--multiquery` run aborts the statements after it. Prod proved that — its
`events_raw` has no TTL, so the schema in this repo and the schema on the
server have drifted. Read the state first and only remove what is there:

```bash
$CH --query "SELECT name, extract(engine_full, 'TTL [^S]*') AS ttl
  FROM system.tables WHERE database = 'clawd'
  AND name IN ('metrics_raw','events_raw') FORMAT PrettyCompact"
```

Then, for each table that came back with a non-empty `ttl`, and only those:

```bash
$CH --query "ALTER TABLE clawd.metrics_raw REMOVE TTL"
$CH --query "ALTER TABLE clawd.events_raw  REMOVE TTL"
```

**Verify — this must come back empty:**

```bash
$CH --query "SELECT name, engine_full FROM system.tables
  WHERE database = 'clawd' AND name IN ('metrics_raw','events_raw') FORMAT Vertical" | grep -i ttl
```

Three additive SQLite changes and one ClickHouse setting. **All of them before

### The SQLite migrations

`drizzle/0010_add_user_timezone.sql`, `0011_add_rank_snapshots.sql`,
`0012_add_profile_settings.sql`. All three are additive: one column with a
DEFAULT, and two new tables. Nothing is rewritten and no existing row changes.

**`bunx drizzle-kit migrate` DOES NOT WORK on this repo** and has not for a
long time: `drizzle/meta/_journal.json` names `0003_certain_baron_strucker`

### The ClickHouse clock

Every hour-of-day, weekday and week figure on a profile is now computed with
`toTimeZone(timestamp, <the user's zone>)`, which converts FROM the column's
timezone. `timestamp` is a `DateTime64(3)` with no zone of its own, so that is
the SERVER timezone — which also parses the UTC literals the app inserts. If it
is anything but UTC, every one of those figures is wrong by the server's offset
AND the stored instants were parsed wrong, which no query can repair later.

```bash
$CH --query "SELECT timezone()"
```

It must print `UTC`. The image defaults to UTC, so it almost certainly does;
`docker/clickhouse/config.xml` now pins it so a host with `TZ` set cannot change
it quietly. If the pin is not live yet it arrives with the next ClickHouse
restart, which is safe to defer — the app retries a refused connection, unlike
the 4xx it treats as permanent.

**No new ClickHouse COLUMNS are needed for anything in this round.** The
ultrathink counter stores its flag as an ordinary `events_raw` row under the
event name `clawdgg.ultrathink`, using columns that already exist. That is
deliberate: a flag is a timestamp and a session id, and api_request reports no
cache-TTL split, so neither gets a column of its own.

## 2. Deploy the new app

Now, while the tables are still the old ones. The new app writes `row_id` into
the old tables, so by the time step 3 copies, the newest rows already carry the
hash and the copy only has to compute the historical ones.

Tag the current image FIRST, so the rollback below has something to go back to:

```bash
ssh clawdgg 'docker tag clawdgg-app:latest clawdgg-app:pre-2026-10'
```

`scripts/deploy.sh` syncs and **builds only** — it deliberately does not start
anything, because the restart is the step with the downtime. So it is two
commands:

```bash
scripts/deploy.sh --dry-run    # read what would change
scripts/deploy.sh              # rsync + `docker compose build app`
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE up -d app"
```

The image is already built at that point, so `up -d` is a container swap of a
second or two — and the OTel SDK retries a connection refusal, unlike the 4xx
it treats as permanent. No batch is lost by it.

**Verify** — run Claude Code locally for a minute, then:

```bash
# row_id is being written, and nothing is empty
$CH --query "
SELECT countIf(row_id = '') AS no_hash, count() AS total
FROM clawd.metrics_raw WHERE timestamp > now() - INTERVAL 10 MINUTE FORMAT Vertical"

# the new columns are actually populated, not silently skipped
$CH --query "
SELECT metric_name, query_source, time_type, count()
FROM clawd.metrics_raw WHERE timestamp > now() - INTERVAL 10 MINUTE
GROUP BY ALL ORDER BY count() DESC FORMAT PrettyCompact"

$CH --query "
SELECT event_name, countIf(event_sequence >= 0) AS with_seq, count()
FROM clawd.events_raw WHERE timestamp > now() - INTERVAL 10 MINUTE
GROUP BY event_name FORMAT PrettyCompact"
```

Expect `no_hash = 0`, a non-empty `query_source` on token/cost rows, both
`user` and `cli` on `active_time.total`, and `with_seq > 0`. A `with_seq` of 0
means the exporter is older than `event.sequence` — not an error, but note it:
those rows rely on the other identity columns.

And the app log should be clean:

```bash
ssh clawdgg "docker compose -f $COMPOSE logs --tail=200 app" | grep -i otel
```

A gzip batch now returns 200. `[OTel] Skipped N unreadable datapoint(s)` is
informational — the good datapoints in that batch landed.

**Rollback:**

```bash
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE stop app \
  && docker tag clawdgg-app:pre-2026-10 clawdgg-app:latest \
  && docker compose -f $COMPOSE up -d app"
```

The old app does not write the new columns; every one has a DEFAULT, so the
tables tolerate it. Rows it writes get `row_id = ''` and step 3's copy computes
their hash in SQL — nothing is lost by rolling back here.

## 3. Create the v2 tables and copy

`2026-10-18_dedup_identity_v2.sql`. Creates `metrics_raw_v2` / `events_raw_v2`
with the final sorting key (ending in `row_id`), **no TTL**, and every column —
minus `tool_parameters`, which is dropped by omission. That omission is what
physically removes the tool arguments prod already stores.

The copy reads the live tables **without `FINAL`** (FINAL would apply the
broken old key one last time and collapse the rows we are recovering) and
without locking them, so the app keeps ingesting throughout.

```bash
$CH --multiquery < docker/clickhouse/migrations/2026-10-18_dedup_identity_v2.sql
```

**Record the watermark first** — step 4's catch-up needs it. Take it *before*
the copy starts and keep it:

```bash
WATERMARK=$($CH --query "SELECT toString(now() - INTERVAL 5 MINUTE)")
echo "$WATERMARK"    # e.g. 2026-10-18 09:25:00
```

Five minutes of overlap is deliberate: re-copying rows is free (same `row_id`,
they collapse under FINAL) and missing one is not.

### Verify the copy

```bash
$CH --multiquery --query "
USE clawd;
SELECT 'metrics raw old' AS k, count() AS v FROM metrics_raw
UNION ALL SELECT 'metrics raw new',   count() FROM metrics_raw_v2
UNION ALL SELECT 'metrics no hash',   countIf(row_id = '') FROM metrics_raw_v2
UNION ALL SELECT 'metrics final old', count() FROM metrics_raw FINAL
UNION ALL SELECT 'metrics final new', count() FROM metrics_raw_v2 FINAL
UNION ALL SELECT 'events raw old',    count() FROM events_raw
UNION ALL SELECT 'events raw new',    count() FROM events_raw_v2
UNION ALL SELECT 'events no hash',    countIf(row_id = '') FROM events_raw_v2
UNION ALL SELECT 'events final old',  count() FROM events_raw FINAL
UNION ALL SELECT 'events final new',  count() FROM events_raw_v2 FINAL
FORMAT PrettyCompact"
```

| Check | Expected |
|---|---|
| `raw new` vs `raw old` | `new` **<=** `old`, by however many rows the app inserted during the copy. Step 4 catches those up. `new > old` means the file was run twice; harmless, they collapse. |
| `no hash` | **0** on both. Non-zero is a bug — stop. |
| `final new` vs `final old` | `new` **>=** `old`. Higher means previously-collapsed rows came back. **Lower is a bug — stop and do not exchange.** |

Headline totals, which may rise but must never fall:

```bash
$CH --multiquery --query "
USE clawd;
SELECT 'tokens old' AS k, toUInt64(sum(value)) AS v FROM metrics_raw     FINAL WHERE metric_name = 'claude_code.token.usage'
UNION ALL SELECT 'tokens new',  toUInt64(sum(value)) FROM metrics_raw_v2 FINAL WHERE metric_name = 'claude_code.token.usage'
UNION ALL SELECT 'prompts old', count() FROM events_raw     FINAL WHERE event_name = 'claude_code.user_prompt' AND command_source != 'builtin'
UNION ALL SELECT 'prompts new', count() FROM events_raw_v2  FINAL WHERE event_name = 'claude_code.user_prompt' AND command_source != 'builtin'
FORMAT PrettyCompact"
```

Spot-check that the copy preserved the hashes the app wrote rather than
recomputing them differently — every recent row should match its source:

```bash
$CH --query "
SELECT count() AS disagreements FROM (
  SELECT o.row_id AS old_hash, n.row_id AS new_hash
  FROM clawd.metrics_raw o
  INNER JOIN clawd.metrics_raw_v2 n USING (row_id)
  WHERE o.row_id != '' AND o.timestamp > now() - INTERVAL 1 DAY
) WHERE old_hash != new_hash FORMAT Vertical"
```

**Rollback:** `DROP TABLE clawd.metrics_raw_v2; DROP TABLE clawd.events_raw_v2;`
The live tables have not been touched.

## 4. Exchange, then catch up

`EXCHANGE TABLES` swaps two names atomically in one statement. No query and no
insert ever sees a missing table, so **the app stays up and no OTLP batch is
refused**. Run the two statements back to back:

```bash
$CH --multiquery --query "
USE clawd;
EXCHANGE TABLES metrics_raw AND metrics_raw_v2;
EXCHANGE TABLES events_raw  AND events_raw_v2;"
```

The names have now traded places: `metrics_raw` is the v2 shape the app writes
to, and `metrics_raw_v2` holds the old rows — **including everything inserted
into the old table between the copy and the exchange**. Copy that tail forward.
The statements are at the bottom of
`2026-10-18_dedup_identity_v2.sql`, commented out, with explicit column lists
(the two tables no longer have the same shape). Substitute `$WATERMARK` from
step 3:

```bash
# Uncomment the two step-4 INSERT ... SELECT blocks, or paste them with the
# watermark bound as a query parameter:
$CH --param_watermark="$WATERMARK" --multiquery < /tmp/step4-catchup.sql
```

This is idempotent: a row already present carries the same `row_id` and
collapses under FINAL. Running it twice is safe; running it late is safe.

**Verify:**

```bash
$CH --query "SELECT name, sorting_key FROM system.tables
  WHERE database = 'clawd' AND name IN ('metrics_raw','events_raw') FORMAT Vertical"
# both sorting keys must end in `row_id`

$CH --multiquery --query "
USE clawd;
SELECT 'tail left behind' AS k,
       (SELECT count() FROM metrics_raw_v2 WHERE timestamp >= toDateTime64('$WATERMARK', 3))
     - (SELECT count() FROM metrics_raw    WHERE timestamp >= toDateTime64('$WATERMARK', 3)) AS v
FORMAT PrettyCompact"
```

`tail left behind` must be `<= 0` (negative just means new live rows arrived,
which is the point). Then re-run the step-0c baseline query against the new
tables: prompts, tokens and cost must be **>=** the step-0c values.

Finally, confirm the TTL did not come along:

```bash
$CH --query "SELECT name, engine_full FROM system.tables
  WHERE database = 'clawd' AND name IN ('metrics_raw','events_raw') FORMAT Vertical" | grep -i ttl
# must be empty
```

### Rollback

Exchange back, then catch up the other way. The old tables are never modified
by the forward path, so this is a true reversal.

```bash
$CH --multiquery --query "
USE clawd;
EXCHANGE TABLES metrics_raw AND metrics_raw_v2;
EXCHANGE TABLES events_raw  AND events_raw_v2;"
```

Then copy the rows the new app wrote while the v2 shape was live back into the
old tables (which answer to `*_v2` again after the exchange) — the ROLLBACK
block at the bottom of the migration file has the exact statements, selecting
only the columns the old shape has. Then roll the image back as in step 2.

Keep `*_v2` (the old tables) for at least two weeks of clean running. Drop only
then, and only after confirming the figures still reconcile:

```bash
$CH --multiquery --query "USE clawd; DROP TABLE metrics_raw_v2; DROP TABLE events_raw_v2;"
```

## 5. Import pre-OTEL `daily_stats` into ClickHouse

> **Deploy the D3 code and run this import back to back.** The D3 commit
> removes every read of `users.legacy_*` and `daily_stats`, so between that
> deploy and this import the pre-OTEL history is briefly **absent** from the
> site. That is the safe ordering: absent is visibly wrong and self-correcting,
> doubled is invisibly wrong. Never the other way round — with the legacy read
> paths still live *and* this import applied, every all-time total doubles.
>
> So: deploy the D3 code (`scripts/deploy.sh` then `up -d app`, as in step 2),
> confirm the site loads, then run the dry run and the `--apply` in the same
> sitting.

The script is at `docker/clickhouse/migrations/2026-10-18_import_daily_stats.ts`
and the app image does **not** contain `docker/` (it is in `.dockerignore`), so
mount the directory in. Parameterised, because the compose file, the service
name and the data volume all live on the server:

```bash
# Adjust COMPOSE / the service name / the DB path to match the server.
# `docker compose config --services` lists the real service names, and
# `docker compose config --volumes` the real volume names.
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE run --rm \
  -v ./docker:/app/docker \
  -e DATABASE_PATH=/data/clawd.db \
  app bun docker/clickhouse/migrations/2026-10-18_import_daily_stats.ts"
```

## 6. Rebuild the token and cost metrics that were already collapsed

`2026-10-19_repair_token_metrics.ts`. **After step 4, never before.**

This is the step that puts the lost tokens back. Steps 1–4 stop the collapsing;
they do not recover what was already merged away — but the measurement is not
actually gone. It is in `events_raw`, where every `api_request` row carries all
four token counters, the model, and Claude Code's own `cost_usd`, for the
single request it describes.

### Why there is anything to recover

Metrics are exported PERIODICALLY: every datapoint in one export interval shares
the export timestamp and differs only by model / query_source / speed, none of
which were in the old metrics key. So an interval covering ten requests
collapsed to one row per token type. Events are log records that carry the
instant they happened, so two of them collide only inside the same millisecond.

Prod, measured 2026-10-18, provenance='live', last 30 days:

| source | tokens |
|---|---|
| `sum(value)` of `claude_code.token.usage` (metrics_raw FINAL) | 9,446,112,211 |
| `sum(input+output+cacheRead+cacheWrite)` of `api_request` (events_raw FINAL) | 25,259,653,024 |

**63% of the tokens were missing**, and `claude_code.cost.usage` collapsed the
same way, so every dollar figure on the site is understated by roughly the same
share. Row counts say it from the other side: 1,477,211 events against 564,972
metrics, where one request should leave one event and four or five metric rows.

### BEFORE: confirm the diagnosis on your own data

Do not run the repair on faith. If metric rows share far fewer timestamps than
there are requests, the export-interval explanation holds. **If `instants` is
close to `requests`, it does not — stop and find the real cause.**

## Known limits after all six steps

- **Collapsed TOKEN and COST rows are recoverable; nothing else is.** Step 6
  rebuilds them from the `api_request` events that measured the same requests.
  Everything else the old metrics key collapsed — lines of code, commits, PRs,
  active time, session counts — has no per-event twin and stays collapsed.
- **Even the repaired figure is a FLOOR.** events_raw's old key ended in
  `timestamp` too, and `session_id` is empty on every live row, so two
  api_requests in the same millisecond collapsed there as well. A collapsed row
  leaves no trace of what it absorbed, so the residual is not knowable after
  the fact; the repair script prints a lower bound on it (the gap between a raw
  and a FINAL count of api_request rows). Publish the repaired totals as "at
  least", not as exact.
- **`session_id` is empty on 100% of live rows, and `decision` on 100% of
  tool_results** (71,478 of 71,478 over 7 days, measured 2026-10-18). Both are
  fixed in the app going forward; the historical rows stay empty, so
  per-session analytics and tool decision-source figures only start from the
  step-2 deploy. The read paths already exclude `session_id = ''`.
- **Legacy days have no detail.** The import reconstructs counts and sums, not
  events: `prompt_length` is 0, `model` and `session_id` are empty, and every
  row sits at 12:00 UTC. The read paths compensate — `provenance='legacy'` is
  excluded from hour-of-day and heatmap queries, `session_id = ''` from
  per-session analytics, `model = ''` from cache-savings, and the daily
  `sessions` figure comes from the `claude_code.session.count` metric rather
  than `uniqExact(session_id)`.
- **`tool_success` is not real on legacy rows.** daily_stats counted tool
  calls, not outcomes, so legacy rows are excluded from success-rate queries
  rather than being reported as 100% successful.
- **Haiku 5.5 long prompts and Opus fast mode are priced only where the input
  says so.** Both are now in `src/lib/pricing.ts`, and the JSONL import reads
  `message.usage.speed` and the request's own token counts. Live OTLP rows
  carry Claude Code's own measured cost and need neither. The ClickHouse
  cache-savings estimate applies fast mode (the rows carry `speed`) but cannot
  apply Haiku's prompt-length tier, which is decided per request.
- **`agent_id` / `parent_agent_id` and a 5m/1h cache-creation split are not
  captured** because the current docs do not define them. Subagent attribution
  is `query_source` + `agent.name`; `api_request` reports one
  `cache_creation_tokens` with no TTL breakdown.
- **`attempt`, `tool_input_size_bytes`, `tool_result_size_bytes`,
  `app.entrypoint`, `ccr.session.id`, `user.id` and `user.email` are not
  stored.** They are emitted, but none can distinguish two records sharing a
  timestamp and a session, and `user.email` is PII with no use here.
