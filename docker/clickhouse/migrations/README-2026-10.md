# Prod runbook — October 2026 OTEL ingestion migration

Seven steps, in this order. Each says how to verify it and how to undo it.

Step 0b is **already done on prod** (2026-10-18). Step 6 is the one that puts
the lost tokens back — read "Why there is anything to recover" before running
anything, because 63% of the live token total is currently missing and that
changes every dollar figure on the site.

**The app stays up for all of them.** That is not a convenience — it is the
whole design. The OTel SDK *drops* a batch it cannot deliver, and Claude Code's
metrics use delta temporality, so a batch refused during a maintenance window
is **gone, not resent**. Any step that stops the app loses exactly the data
this migration exists to protect. `EXCHANGE TABLES` is what makes that possible.

**Server:** `clawdgg` (46.224.85.32) · **Compose file (on the server, not in
this repo):** `/opt/clawdgg/docker-compose.staging.yml`

Shorthand — paste both into the shell you are going to work in:

```bash
COMPOSE=/opt/clawdgg/docker-compose.staging.yml
ch() {
  q=''
  for a in "$@"; do q="$q '$(printf '%s' "$a" | sed "s/'/'\\\\''/g")'"; done
  ssh clawdgg "docker compose -f $COMPOSE exec -T clickhouse clickhouse-client --multiquery$q"
}
```

`ch` takes its SQL on STDIN, so every query below is a here-doc:

```bash
ch <<'SQL'
SELECT 1
SQL
```

It is a FUNCTION, and not the `CH="ssh …"` variable this used to be, because
that variable was not copy-pasteable. Expanding it put the SQL inside the double
quotes of an `ssh` argument, so every quote in the query had to survive two
levels of shell parsing to arrive intact — and in a shell where `CH` was not
defined (a new window, a `set -u`, the second half of a long session) the line
ran the first flag as a command instead of failing. On stdin the SQL arrives
verbatim. The quoted here-doc delimiter is what keeps the local shell off a `$`
or a backtick inside it; the few queries that DO need a local value take it as
a ClickHouse parameter (`--param_x=…` on the `ch` line, `{x:String}` in the
query) rather than by interpolation.

The re-quoting loop is why those parameters survive: the arguments are quoted
for the REMOTE shell, which would otherwise split `--param_watermark=2026-10-18
09:25:00` at its space and pass ClickHouse two half-arguments. `$q` is empty for
a bare `ch`, so it does not hand it an empty argument either.

**It is a `sed` quoter and not `printf '%q '`, which this used to be, because
`%q` is a bash/zsh extension.** dash's builtin `printf` has no such directive:
it prints `printf: %q: invalid directive`, the parameter never reaches
ClickHouse, and the query dies on `Substitution 'watermark' is not set
(UNKNOWN_QUERY_PARAMETER)`. The old note claimed dash was checked; it was not.
That matters because `/bin/sh` IS dash on Debian and Ubuntu, and the instruction
above is to paste this into whatever shell you are working in. The loop above is
plain POSIX — verified under bash, zsh and dash, with a value containing a space.

Every `docker compose` command below — `ch` included — takes the compose file
from `$COMPOSE`, so if the prod file is ever renamed, change it in one place.

## What has been verified, and how

Unlike the previous version of this runbook, the identity hash is no longer
asserted on reasoning alone.

`docker/clickhouse/migrations/identity-parity.test.ts` inserts 15 rows through
the **real** serialisation path (the JSONEachRow body `src/db/clickhouse.ts`
sends) into the **real** DDL, and asserts ClickHouse's own expression
recomputes the row_id TypeScript computed — over empty strings, column
defaults, CJK and Greek text, a surrogate pair split at a truncation boundary,
`provenance` values other than the default, millisecond edges, and
`event_sequence` at `Number.MAX_SAFE_INTEGER`. Run it before trusting step 3:

```bash
cd /path/to/clawdgg
curl https://clickhouse.com/ | sh          # ~182 MiB standalone binary, no server
CLICKHOUSE_BIN=./clickhouse bun test docker/clickhouse/migrations
```

**That binary is NEWER than prod's engine, and the suite cannot be run on
prod's.** `curl https://clickhouse.com/ | sh` installs the current release;
prod is 24.3.18.7, whose `clickhouse local --multiquery` reads only the FIRST
inline row after a `FORMAT JSONEachRow` and then tries to parse the second as
SQL (`Syntax error: failed at position 1 ('{')`). So these scripts do not run
there at all — measured against 24.3.18.7. The parity it proves still holds:
`SHA256`, `arrayStringConcat` and `char(31)` have not changed semantics. But
the engine-version-specific proof on 24.3 is the SERVER-side one, which this
runbook now makes twice over at step 3: `no hash = 0` on both v2 tables, and
the `NOT IN` spot-check that every hash the app itself computed survived the
copy. Both were run on a 24.3.18.7 server carrying prod's exact DDL.

Two things that test established, both of which shaped the steps below:

1. **`input_format_skip_unknown_fields` defaults to `1`.** A JSON body naming a
   column the table does not have is **silently accepted and the value
   dropped**. The old claim that "the insert fails loudly on an unknown column"
   is false, so the column-ordering in step 1 cannot be enforced by waiting for
   an error — step 2 verifies the columns **positively** before deploying, and
   step 2's post-deploy check looks for a non-empty `row_id` rather than for an
   absent exception.
2. **A lone surrogate rejects the whole batch.** `JSON.stringify` of a string
   truncated mid-emoji emits a bare `\ud83d`, and ClickHouse answers
   `CANNOT_PARSE_ESCAPE_SEQUENCE` for the **entire** insert. `insert()` now
   replaces unpaired surrogates with U+FFFD, which is what Node's UTF-8
   encoding does anyway — so the row_id is unchanged by it.

## 0. Back up, remove the TTLs, record the baseline, apply `pricing_source`

### 0a. Backups

`EXCHANGE` is cheap to reverse, but a bad `INSERT ... SELECT` is not, and the
daily_stats import is not reversible at all. Take both.

**`BACKUP ... TO Disk('backups', …)` DOES NOT WORK HERE.** It was in this
runbook and it fails twice: `BACKUP TABLE a, b` is a syntax error (each name
needs its own `TABLE` keyword), and with that fixed it answers `The
'backups.allowed_disk' configuration parameter is not set, cannot use 'Disk'
backup engine (INVALID_CONFIG_PARAMETER)` — `docker/clickhouse/config.xml`
configures no `backups` disk, and `system.disks` lists only `default`.

So the backup is an in-server copy of each table, which needs no configuration
and no file to move. The two raw tables are about 25 MB together
(`sum(bytes_on_disk)` over `system.parts`), so this costs seconds.

**`ENGINE = MergeTree ORDER BY tuple()` is the whole point of the explicit
engine.** `CREATE TABLE … AS metrics_raw` alone would copy the
ReplacingMergeTree and its sorting key, and a backup that dedups is not a
backup — it would collapse exactly the rows this migration exists to keep. A
plain MergeTree ordered by nothing stores every row it is given, so the count
check below is exact.

```bash
# a) In-server copy of the two raw tables. Run BEFORE step 1, so these carry
#    the current (pre-migration) column set — see the restore note below.
ch <<'SQL'
USE clawd;
CREATE TABLE IF NOT EXISTS metrics_raw_bak_2026_10 AS metrics_raw ENGINE = MergeTree ORDER BY tuple();
CREATE TABLE IF NOT EXISTS events_raw_bak_2026_10  AS events_raw  ENGINE = MergeTree ORDER BY tuple();
INSERT INTO metrics_raw_bak_2026_10 SELECT * FROM metrics_raw;
INSERT INTO events_raw_bak_2026_10  SELECT * FROM events_raw;
SQL

# The count check. These must be EQUAL — not >=, not close.
ch <<'SQL'
USE clawd;
SELECT * FROM (
  SELECT 'metrics live' AS k, count() AS v FROM metrics_raw
  UNION ALL SELECT 'metrics bak', count() FROM metrics_raw_bak_2026_10
  UNION ALL SELECT 'events live', count() FROM events_raw
  UNION ALL SELECT 'events bak',  count() FROM events_raw_bak_2026_10
) ORDER BY k FORMAT PrettyCompact
SQL
```

**The restore path, and why it is not `SELECT *`.** Step 1 adds columns to the
live tables, so from then on the backup is NARROWER than its table and
`INSERT INTO metrics_raw SELECT * FROM metrics_raw_bak_2026_10` answers `Number
of columns doesn't match (source: 15 and result: 30)`. Name the BACKUP's columns
on the INSERT and they line up by position; the added columns take their
DEFAULTs, which is what the pre-migration rows had anyway (`row_id = ''`, which
the step-3 copy recomputes in SQL). And TRUNCATE first — restoring on top of a
live table under the v2 key ADDS the old rows rather than replacing them.

```bash
# The backup's own column list, in its own order — read it, do not type it.
ch <<'SQL'
SELECT arrayStringConcat(groupArray(name), ', ') AS cols FROM (
  SELECT name FROM system.columns
  WHERE database = 'clawd' AND table = 'metrics_raw_bak_2026_10' ORDER BY position
) FORMAT TSVRaw
SQL

# Then, with that list pasted in (metrics_raw shown; events_raw is the same shape):
ch <<'SQL'
USE clawd;
TRUNCATE TABLE metrics_raw;
INSERT INTO metrics_raw (timestamp, user_id, session_id, metric_name, value, model,
    token_type, line_type, terminal_type, app_version, account_uuid, tool, decision,
    language, provenance)
SELECT * FROM metrics_raw_bak_2026_10;
SQL
```

Keep both `*_bak_2026_10` tables as long as `metrics_raw_v2` — two weeks of
clean running — then drop them with it.

```bash
# b) The SQLite users/daily_stats DB, which the step-5 import reads.
#    NOTE: the app image is slim and has NO `sqlite3` CLI. Use bun:sqlite,
#    which is in the runtime, and its online .backup — a file copy of a live
#    WAL database can be torn.
ssh clawdgg "docker compose -f $COMPOSE exec -T app bun -e '
  const { Database } = require(\"bun:sqlite\");

  db.exec(\"VACUUM INTO \x27/data/clawd.pre_2026_10.db\x27\");
  console.log(\"ok\");
'"
```

Verify the SQLite copy is readable and complete before continuing:

```bash
ssh clawdgg "docker compose -f $COMPOSE exec -T app bun -e '
```

### 0b. Remove the TTLs — do this BEFORE the copy

> **DONE on prod, 2026-10-18 16:05 UTC.** `metrics_raw` had its TTL removed;
> `events_raw` **never had one** and answered `Table doesn't have any table TTL
> expression`. Both verified clear afterwards, at 564,972 and 1,477,211 rows.
> Re-read 0b only if you are migrating a different instance.

The schema says both raw tables carry `TTL toDateTime(timestamp) + INTERVAL 365
DAY`, which silently deletes a user's first year the moment it turns 366 days
old — the opposite of what the daily_stats import is for. The v2 tables have no
TTL, and the OLD tables must lose theirs too, or rows can expire out from under
the copy between step 3 and step 4.

**ASK BEFORE REMOVING.** `REMOVE TTL` on a table that has none is NOT a no-op:
it raises `Table doesn't have any table TTL expression`, which in a
`--multiquery` run aborts the statements after it. Prod proved that — its
`events_raw` has no TTL, so the schema in this repo and the schema on the
server have drifted. Read the state first and only remove what is there:

```bash
ch <<'SQL'
SELECT name, extract(engine_full, 'TTL [^S]*') AS ttl
  FROM system.tables WHERE database = 'clawd'
  AND name IN ('metrics_raw','events_raw') FORMAT PrettyCompact
SQL
```

Then, for each table that came back with a non-empty `ttl`, and only those:

```bash
ch <<'SQL'
ALTER TABLE clawd.metrics_raw REMOVE TTL
SQL
ch <<'SQL'
ALTER TABLE clawd.events_raw  REMOVE TTL
SQL
```

**Verify — this must come back empty:**

```bash
ch <<'SQL' | grep -i ttl
SELECT name, engine_full FROM system.tables
  WHERE database = 'clawd' AND name IN ('metrics_raw','events_raw') FORMAT Vertical
SQL
```

### 0c. Baseline numbers

Every later step is checked against these. Keep the output.

**No `command_source` in this query, deliberately.** The previous version
filtered `command_source != 'builtin'` — a column step 1 has not added yet. The
whole statement then dies on `Unknown expression or function identifier
'command_source' (UNKNOWN_IDENTIFIER)`, so the operator gets no baseline at all,
not six of seven rows. `user_prompt rows` counts every one of them instead,
which is the only honest pre-step-1 figure: before the column exists, a builtin
slash command and a real prompt are the same row. **Step 4 re-runs THIS query,
unchanged**, so the two sides compare like for like — see the note there.

The whole thing is wrapped in a subquery with an `ORDER BY` so the rows come
back in a fixed order. Without it the keys arrive in whatever order the blocks
finish in, and the step-4 comparison is a diff you cannot read.

```bash
ch <<'SQL'
USE clawd;
SELECT * FROM (
  SELECT 'metrics raw'      AS k, count() AS v FROM metrics_raw
  UNION ALL SELECT 'metrics final',    count() FROM metrics_raw FINAL
  UNION ALL SELECT 'events raw',       count() FROM events_raw
  UNION ALL SELECT 'events final',     count() FROM events_raw FINAL
  UNION ALL SELECT 'user_prompt rows', count() FROM events_raw FINAL WHERE event_name = 'claude_code.user_prompt'
  UNION ALL SELECT 'tokens',           toUInt64(sum(value)) FROM metrics_raw FINAL WHERE metric_name = 'claude_code.token.usage'
  UNION ALL SELECT 'cost cents',       toUInt64(sum(value) * 100) FROM metrics_raw FINAL WHERE metric_name = 'claude_code.cost.usage'
) ORDER BY k FORMAT PrettyCompact
SQL
```

**Rollback:** nothing to undo. Re-adding a TTL would delete data; don't.

## 1-bis. SQLite columns and tables, and the ClickHouse clock

Five additive SQLite migrations and one ClickHouse setting. **All of them before
the step-2 deploy**, for the same reason step 1 comes before it: the new app
SELECTs these columns by name, and a missing one is an error on every request
that touches it — not a degraded page.

### The SQLite migrations

`drizzle/0008_add_plan_usage_snapshots.sql` through `0012_add_profile_settings.sql`
— **five, not three.** Prod is missing `plan_usage_snapshots` (0008) and
`device_tokens` (0009) as well, which the previous version of this step did not
create at all; step 6's plan-usage freshness check reads `plan_usage_snapshots`
and would have failed on a table that was never made. 0007 and 0013 are already
on prod. All five are additive: one column with a DEFAULT, four new tables, and
their indexes. Nothing is rewritten and no existing row changes.

**All of them before the deploy, or the HOMEPAGE 500s** — not a panel, the page.
`/` reads `rank_snapshots` (0011) for the board arrows and `profile_settings`
(0012) for what a profile shows, and every "when" read needs `users.timezone`
(0010). A missing table is an exception on the first query, which is the one
that renders the page.

**`bunx drizzle-kit migrate` DOES NOT WORK on this database.** Not because the
chain is broken — commit 8f73087 fixed that — but because prod's
`__drizzle_migrations` was never stamped, so a `migrate` replays from 0003 and
dies on `duplicate column name: input_tokens`. See 1-ter. So the five files are
applied directly, statement by statement.

**Apply the FILES, verbatim. Do not retype their SQL.** The version of this step
that did carried
`ALTER TABLE users ADD COLUMN timezone text NOT NULL DEFAULT ("UTC")`, which
SQLite **rejects**: inside the parentheses `"UTC"` parses as an identifier, not
a string, and the answer is `default value of column [timezone] is not
constant`. The loop's `try/catch` then printed it as `skip … default value of
column [timezone] is not constant` — and this step told you a `skip` was the
expected answer on a re-run. So the one statement that mattered failed, said
`skip`, and the homepage would have 500'd on the next deploy. The file says
`DEFAULT 'UTC'` and works. Measured on a copy of prod's schema.

The runner below therefore (a) reads the SQL out of `drizzle/`, (b) splits on
drizzle's own `--> statement-breakpoint`, and (c) distinguishes an
already-applied statement from a real failure and **exits non-zero** on the
latter, instead of printing both as `skip`.

Build it locally, from this repo:

```bash
cd /path/to/clawdgg
bun -e '
const { readFileSync } = require("node:fs");
const TAGS = ["0008_add_plan_usage_snapshots", "0009_add_device_tokens",
  "0010_add_user_timezone", "0011_add_rank_snapshots", "0012_add_profile_settings"];
const out = [
  `const { Database } = require("bun:sqlite");`,
  `const db = new Database(process.env.DATABASE_PATH ?? "/data/clawd.db");`,
  `let real = 0;`,
  `const BENIGN = /duplicate column name|already exists/i;`,
  `const run = (tag, sql) => {`,
  `  for (const stmt of sql.split("--> statement-breakpoint").map(s => s.trim()).filter(Boolean)) {`,
  `    const label = tag + "  " + stmt.replace(/\\s+/g, " ").slice(0, 64);`,
  `    try { db.exec(stmt); console.log("ok    ", label); }`,
  `    catch (e) {`,
  `      const msg = String(e.message);`,
  `      if (BENIGN.test(msg)) console.log("skip  ", label, "--", msg);`,
  `      else { real++; console.log("FAILED", label, "--", msg); }`,
  `    }`,
  `  }`,
  `};`,
];
for (const tag of TAGS) out.push(`run(${JSON.stringify(tag)}, ${JSON.stringify(readFileSync(`drizzle/${tag}.sql`, "utf8"))});`);
out.push(`if (real > 0) { console.log("\\n" + real + " statement(s) FAILED - stop and read them."); process.exit(1); }`);
out.push(`console.log("\\nall statements accounted for");`);
console.log(out.join("\n"));
' > /tmp/step-1bis.js
```

Then pipe that one file into the RUNNING container. **Not `-v ./drizzle:…` and
not `/app/drizzle`:** the image running on prod predates the Dockerfile that
copies `drizzle/` in (see 1-ter), so the files may simply not be there — and a
self-contained file has no second copy of the SQL to drift from.

```bash
COMPOSE=/opt/clawdgg/docker-compose.staging.yml
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE exec -T \
  -e DATABASE_PATH=/data/clawd.db app \
  sh -c 'cat > /tmp/step-1bis.js && bun /tmp/step-1bis.js'" < /tmp/step-1bis.js
```

Every line must read `ok` on the first run and `skip` on a second — nine
statements across the five files. A `FAILED` line is not a skip: stop and read it.

**Verify:**

```bash
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE exec -T app bun -e '
  const { Database } = require(\"bun:sqlite\");
  const db = new Database(process.env.DATABASE_PATH ?? \"/data/clawd.db\", { readonly: true });
  console.log(db.query(\"SELECT timezone, count(*) n FROM users GROUP BY timezone\").all());
  console.log(db.query(\"SELECT name FROM sqlite_master WHERE type = \x27table\x27 AND name IN (\x27plan_usage_snapshots\x27,\x27device_tokens\x27,\x27rank_snapshots\x27,\x27profile_settings\x27) ORDER BY name\").all());
```

Nobody has a real zone yet — `clawdgg setup` reports it, and until then UTC is

### 1-ter. Stamp the Drizzle journal — AFTER THE STEP-2 DEPLOY

**This one step does NOT belong before step 2, and the previous version of this
runbook put it there.** The stamp runs `bun scripts/check-migrations.ts`, and
`COPY --from=builder /app/scripts ./scripts` only entered the Dockerfile on
2026-10-18 (commit 6d6d78f). The image prod is running right now has no
`scripts/` directory, so that command is `bun: can't open file` — on the deploy
window, after the backup, for nothing.

**Deferring it is safe, and that is not a guess about this app: it does not
migrate on boot.** Nothing in `src/` calls drizzle's migrator, so an unstamped
`__drizzle_migrations` changes no behaviour; it only decides what a FUTURE
`drizzle-kit migrate` would replay, and nobody runs one during this migration.
So the order is: 1-bis's five files by hand → step 2's deploy → this stamp. Once
the new image is up, `scripts/` is there and the command below works as written.

**Do not run `drizzle-kit migrate` on prod before this.** The chain is
replayable again (commit 8f73087), but prod's `__drizzle_migrations` was never
stamped: `migrate` has failed there since the 0003 rename, so prod's schema has
been maintained by hand ever since while the journal stayed at the point it
broke. A plain `migrate` now would replay the whole chain from there and die on
`duplicate column name: input_tokens`. It rolls back and loses no data, but it
also achieves nothing and takes a deploy window to find out.

**THE ONE PATH, and the order is forced.** `--stamp` compares the database
against `src/db/schema.ts` and refuses on any mismatch, so it cannot be run
before 0008–0012 are in place — and once they are, the schema matches and the
stamp is just bookkeeping. So: apply the five files in 1-bis by hand, deploy
step 2, then stamp, and `drizzle-kit migrate` is the path for 0014 onward. There
is no variant where `migrate` applies 0008–0012 on this database.

Rehearsed on a copy of prod's schema: with 0008–0012 applied and nothing else,
`--stamp` answers `✓ … matches src/db/schema.ts` and
`✓ stamped 0013_dashboard_v2_archetypes (created_at 1794300000000)` — which is
the `m >= 1794300000000` the read-only check below is looking for. It is also an
independent confirmation that 0008–0012 are the ONLY migrations prod is missing:
had anything else been absent, `--stamp` would have refused with the diff.

```bash

# (a) Read-only: is it already stamped? m >= 1794300000000 means nothing to do.
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE exec -T app bun -e '
  const { Database } = require(\"bun:sqlite\");
  const db = new Database(process.env.DATABASE_PATH ?? \"/data/clawd.db\", { readonly: true });
  try {
    console.log(db.query(\"SELECT MAX(created_at) m, COUNT(*) n FROM __drizzle_migrations\").get());
  } catch (e) { console.log(\"no journal table:\", String(e.message)); }
'"

# (b) Back up first. Same online .backup as step 0a, because this writes.
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE exec -T app bun -e '
  const { Database } = require(\"bun:sqlite\");
  const db = new Database(process.env.DATABASE_PATH ?? \"/data/clawd.db\", { readonly: true });
  db.exec(\"VACUUM INTO \x27/data/clawd.pre_stamp.db\x27\"); console.log(\"ok\");
'"

# (c) Stamp. Verifies the schema against src/db/schema.ts FIRST and refuses on
#     a mismatch; executes no migration SQL; touches only __drizzle_migrations.
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE exec -T app \

```

A refusal is the useful answer: it means prod's schema and `src/db/schema.ts`
disagree about something, and that has to be reconciled by hand before any
`migrate` is safe. Read the diff it prints; do not stamp around it.

Any NEW migration is `0014` or later — `0013` is taken by the relocated
archetypes file — and `drizzle/meta/_journal.json` has to name it.

### The ClickHouse clock

Every hour-of-day, weekday and week figure on a profile is now computed with
`toTimeZone(timestamp, <the user's zone>)`, which converts FROM the column's
timezone. `timestamp` is a `DateTime64(3)` with no zone of its own, so that is
the SERVER timezone — which also parses the UTC literals the app inserts. If it
is anything but UTC, every one of those figures is wrong by the server's offset
AND the stored instants were parsed wrong, which no query can repair later.

```bash
ch <<'SQL'
SELECT timezone()
SQL
```

It must print `UTC`. The image defaults to UTC, so it almost certainly does;
`docker/clickhouse/config.xml` now pins it so a host with `TZ` set cannot change
it quietly. If the pin is not live yet it arrives with the next ClickHouse
restart, which is safe to defer — the app retries a refused connection, unlike
the 4xx it treats as permanent.

**No new ClickHouse COLUMNS are needed for anything in this round.** The
ultrathink counter stores its flag as an ordinary `events_raw` row under the
event name `clawdgg.ultrathink`, using columns that already exist. That is
deliberate: a flag is a timestamp and a session id, and api_request reports no
cache-TTL split, so neither gets a column of its own.

## 2. Deploy the new app

Now, while the tables are still the old ones. The new app writes `row_id` into
the old tables, so by the time step 3 copies, the newest rows already carry the
hash and the copy only has to compute the historical ones.

**1-ter comes after this, not before it** — it is filed with the rest of the
SQLite work to keep that together, but the stamp needs `scripts/` and only the
image you are about to deploy has it. 1-bis's five migrations DO come first.

Tag the current image FIRST, so the rollback below has something to go back to:

```bash

```

`scripts/deploy.sh` is in the repository and is the authority on what it does to
the server — it overwrites the compose file and the Caddyfile, and it PRINTS the
release-day switch-over itself. Read its `--dry-run` output rather than trusting
a copy of its steps here. Everything in this runbook uses
`docker-compose.staging.yml`, which is what prod runs.

It syncs and **builds only** — it deliberately does not start anything, because
the restart is the step with the downtime. So it is two commands:

```bash
scripts/deploy.sh --dry-run    # read what would change
scripts/deploy.sh              # rsync + `docker compose build app`
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE up -d --no-deps app"
```

The image is already built at that point, so `up -d` is a container swap of a
second or two — and the OTel SDK retries a connection refusal, unlike the 4xx
it treats as permanent. No batch is lost by it.

**`--no-deps` on every `up -d` in this runbook, and it is not cosmetic.**
Without it, compose brings up the service's dependencies too: `up -d app`
considers CLICKHOUSE, in the middle of a migration, and recreates it if its
definition has drifted at all — which is a restart of the database this whole
procedure is about, during the one step that is supposed to be a container swap.
The same flag on `up -d caddy` keeps it from recreating the app as a side
effect of touching the proxy.

**And on every `docker compose run --rm` in this runbook, for the same reason.**
`run` starts linked services too unless told not to (`--no-deps: Don't start
linked services`), so a one-shot `run --rm app bun …` in step 5 or step 6 can
reach for ClickHouse in the middle of the migration exactly as `up -d` can. The
earlier version of this runbook had the flag on `up -d` and not on `run`, which
left the hazard it warns about open in four places. Where the command needs no
extra mount, prefer `exec -T` outright: it touches nothing but the container
that is already up.

**Verify** — run Claude Code locally for a minute, then:

#### The rollback one-liner, and the one not to run

To put the app back on whatever image `clawdgg-app:latest` now points at —
after a `docker tag`, or to restart it with a changed `/opt/clawdgg/.env`:

```bash
ssh clawdgg 'cd /opt/clawdgg && docker compose -f docker-compose.staging.yml up -d --no-deps --force-recreate app'
```

`--force-recreate` because a plain `up -d` is a no-op when the service
definition has not changed, which is the case after a tag has moved `:latest`
under it; `--no-deps` so ClickHouse is not recreated alongside; and the
container reads the `.env` afresh on recreation, which a `restart` does not.

**Not `docker compose down && docker compose up -d`.** Older notes carry that

SERVER's own file, which defines Caddy and not the app — so it acts on the
wrong services; and `down` stops every service in whichever file it picked and
removes the network, which takes the site off the air (and, in this migration,
stops the ingestion the whole procedure exists to protect) instead of swapping
one container.

## 3. Create the v2 tables and copy

`2026-10-18_dedup_identity_v2.sql`. Creates `metrics_raw_v2` / `events_raw_v2`
with the final sorting key (ending in `row_id`), **no TTL**, and every column —
minus `tool_parameters`, which is dropped by omission. That omission is what
physically removes the tool arguments prod already stores.

The copy reads the live tables **without `FINAL`** (FINAL would apply the
broken old key one last time and collapse the rows we are recovering) and
without locking them, so the app keeps ingesting throughout.

**Record the watermark BEFORE the copy, and keep it** — step 4's catch-up reads
it to find the rows the app inserted while the copy was running:

```bash
WATERMARK=$(ch <<'SQL'
SELECT toString(now() - INTERVAL 5 MINUTE)
SQL
)
echo "$WATERMARK"    # e.g. 2026-10-18 09:25:00
```

The order matters, and this runbook had it the wrong way round. A watermark
taken AFTER the copy is five minutes before the copy ENDED, so every row the
app inserted between the start of the copy and that instant is in neither the
catch-up window nor the copy — and the copy takes minutes. Taken first, the
window provably covers everything the copy might have missed.

Five minutes of overlap is deliberate: re-copying rows is free (same `row_id`,
they collapse under FINAL) and missing one is not.

Now the copy:

```bash
ch < docker/clickhouse/migrations/2026-10-18_dedup_identity_v2.sql
```

### Verify the copy

```bash
ch <<'SQL'
USE clawd;
SELECT 'metrics raw old' AS k, count() AS v FROM metrics_raw
UNION ALL SELECT 'metrics raw new',   count() FROM metrics_raw_v2
UNION ALL SELECT 'metrics no hash',   countIf(row_id = '') FROM metrics_raw_v2
UNION ALL SELECT 'metrics final old', count() FROM metrics_raw FINAL
UNION ALL SELECT 'metrics final new', count() FROM metrics_raw_v2 FINAL
UNION ALL SELECT 'events raw old',    count() FROM events_raw
UNION ALL SELECT 'events raw new',    count() FROM events_raw_v2
UNION ALL SELECT 'events no hash',    countIf(row_id = '') FROM events_raw_v2
UNION ALL SELECT 'events final old',  count() FROM events_raw FINAL
UNION ALL SELECT 'events final new',  count() FROM events_raw_v2 FINAL
FORMAT PrettyCompact
SQL
```

| Check | Expected |
|---|---|
| `raw new` vs `raw old` | `new` **<=** `old`, by however many rows the app inserted during the copy. Step 4 catches those up. `new > old` means the file was run twice; harmless, they collapse. |
| `no hash` | **0** on both. Non-zero is a bug — stop. |
| `final new` vs `final old` | `new` **>=** `old`. Higher means previously-collapsed rows came back. **Lower is a bug — stop and do not exchange.** |

Headline totals, which may rise but must never fall:

```bash
ch <<'SQL'
USE clawd;
SELECT 'tokens old' AS k, toUInt64(sum(value)) AS v FROM metrics_raw     FINAL WHERE metric_name = 'claude_code.token.usage'
UNION ALL SELECT 'tokens new',  toUInt64(sum(value)) FROM metrics_raw_v2 FINAL WHERE metric_name = 'claude_code.token.usage'
UNION ALL SELECT 'prompts old', count() FROM events_raw     FINAL WHERE event_name = 'claude_code.user_prompt' AND command_source != 'builtin'
UNION ALL SELECT 'prompts new', count() FROM events_raw_v2  FINAL WHERE event_name = 'claude_code.user_prompt' AND command_source != 'builtin'
FORMAT PrettyCompact
SQL
```

Spot-check that the copy carried every hash the app wrote, rather than
recomputing some of them differently — a row the app hashed must be findable in
v2 under that same hash:

```bash
ch <<'SQL'
SELECT count() AS recent_rows_missing_from_v2
FROM clawd.metrics_raw o
WHERE o.row_id != ''
  AND o.timestamp > now() - INTERVAL 1 DAY
  AND o.row_id NOT IN (SELECT row_id FROM clawd.metrics_raw_v2)
FORMAT Vertical
SQL
```

Must be `0`. A non-zero answer names the real failure: the copy's
`if(row_id != '', row_id, <expr>)` did not keep the app's hash.

**This replaces a check that could not fail.** The previous version joined
`metrics_raw` to `metrics_raw_v2` `USING (row_id)` and then compared
`o.row_id != n.row_id` — which the join has just made equal by definition, so
the count was 0 whatever had happened. Verified by substituting a deliberately
wrong hash on the v2 side: the old query still answered `0`, because the join
then matched nothing and `count()` of nothing is also 0. It said `0` when the
copy was right and `0` when it was broken. The `NOT IN` above is falsifiable —
withholding one real `row_id` from the v2 side makes it answer `1`.

**Rollback:** `DROP TABLE clawd.metrics_raw_v2; DROP TABLE clawd.events_raw_v2;`
The live tables have not been touched.

## 4. Exchange, then catch up

`EXCHANGE TABLES` swaps two names atomically in one statement. No query and no
insert ever sees a missing table, so **the app stays up and no OTLP batch is
refused**. Run the two statements back to back:

```bash
ch <<'SQL'
USE clawd;
EXCHANGE TABLES metrics_raw AND metrics_raw_v2;
EXCHANGE TABLES events_raw  AND events_raw_v2;
SQL
```

The names have now traded places: `metrics_raw` is the v2 shape the app writes
to, and `metrics_raw_v2` holds the old rows — **including everything inserted
into the old table between the copy and the exchange**. Copy that tail forward.
The statements are at the bottom of
`2026-10-18_dedup_identity_v2.sql`, commented out, with explicit column lists
(the two tables no longer have the same shape). Substitute `$WATERMARK` from
step 3:

**Extract them with the command below rather than by hand.** The file contains
TWO near-identical pairs of these blocks — the step-4 catch-up and the ROLLBACK
catch-up, which read `FROM metrics_raw_v2` just the same — and the one you want
is the pair above the `-- ROLLBACK:` marker. Uncommenting by eye is how the
rollback gets pasted at step 4.

```bash
F=docker/clickhouse/migrations/2026-10-18_dedup_identity_v2.sql
{ echo 'USE clawd;'
  awk '/^-- 4\. SWAP, WITHOUT STOPPING THE APP\./ {on=1} /^-- ROLLBACK:/ {on=0} on' "$F" \
    | grep -E '^-- *(INSERT|SELECT|FROM|WHERE|   )' | sed 's/^-- \{0,1\}//'
} > /tmp/step4-catchup.sql

# 33 lines, two INSERTs, both ending in `WHERE timestamp >= …{watermark:String}`.
grep -n 'INSERT INTO\|WHERE timestamp' /tmp/step4-catchup.sql

ch --param_watermark="$WATERMARK" < /tmp/step4-catchup.sql
```

This is idempotent: a row already present carries the same `row_id` and
collapses under FINAL. Running it twice is safe; running it late is safe.

**Verify:**

```bash
ch <<'SQL'
SELECT name, sorting_key FROM system.tables
  WHERE database = 'clawd' AND name IN ('metrics_raw','events_raw') FORMAT Vertical
SQL
# both sorting keys must end in `row_id`

ch --param_watermark="$WATERMARK" <<'SQL'
USE clawd;
SELECT 'tail left behind' AS k,
       (SELECT count() FROM metrics_raw_v2 WHERE timestamp >= toDateTime64({watermark:String}, 3))
     - (SELECT count() FROM metrics_raw    WHERE timestamp >= toDateTime64({watermark:String}, 3)) AS v
FORMAT PrettyCompact
SQL
```

`tail left behind` must be `<= 0` (negative just means new live rows arrived,
which is the point). Then re-run **the step-0c query, unchanged**, against the
new tables: every figure must be **>=** its step-0c value. Re-running it
unchanged is what makes that true — a version that filtered
`command_source != 'builtin'` would compare an honest prompt count against a
baseline that could not compute one, and once the new app is deployed the
builtin slash commands start carrying that attribute, so the filtered number
can legitimately come out LOWER than the baseline and look like loss.

`metrics raw` > `metrics final` is expected here and was not true at step 0c:
the catch-up re-copied rows the main copy already had, and they carry the same
`row_id`, so they are waiting to collapse. That is the idempotency working.

### Now the collision check that step 2 could not make

This is the assertion the deploy was for, and it has to be made on rows written
**after** the exchange. Rows written before it went into the old table under the
old key and were collapsed on the way in; nothing here brings them back. Right

So: run Claude Code for a minute, THEN:

```bash
SQL
```

**Both `user` and `cli` must come back**, and the token rows must show more than

## 5. Import pre-OTEL `daily_stats` into ClickHouse

> **Deploy the D3 code and run this import back to back.** The D3 commit
> removes every read of `users.legacy_*` and `daily_stats`, so between that
> deploy and this import the pre-OTEL history is briefly **absent** from the
> site. That is the safe ordering: absent is visibly wrong and self-correcting,
> doubled is invisibly wrong. Never the other way round — with the legacy read
> paths still live *and* this import applied, every all-time total doubles.
>
> So: deploy the D3 code (`scripts/deploy.sh` then `up -d --no-deps app`, as in
> step 2),
> confirm the site loads, then run the dry run and the `--apply` in the same
> sitting.

The script is at `docker/clickhouse/migrations/2026-10-18_import_daily_stats.ts`
and the app image does **not** contain `docker/` — not because `.dockerignore`
excludes it (it does not), but because the runtime stage copies a named list of
directories and `docker/` is not on it — so
mount the directory in. Parameterised, because the compose file, the service
name and the data volume all live on the server:

```bash
# Adjust COMPOSE / the service name / the DB path to match the server.
# `docker compose config --services` lists the real service names, and
# `docker compose config --volumes` the real volume names.
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE run --rm --no-deps \
  -v ./docker:/app/docker \
  -e DATABASE_PATH=/data/clawd.db \
  app bun docker/clickhouse/migrations/2026-10-18_import_daily_stats.ts"
```

Read the summary: days, prompts, tool calls, tokens and cost per user, plus the
days it is **skipping** because ClickHouse already has rows of another
provenance for them (`live`, `backfill`, `backfill-history`, `import`). A
skipped day is the double-count guard doing its job; a long list of them for a
user means that user's OTEL or backfill data already covers the period.

Then the same command with `--apply` appended.

**Verify** — the imported rows reproduce the SQLite numbers:

```bash
ch <<'SQL'
SELECT user_id,
       count(DISTINCT toDate(timestamp)) AS days,
       countIf(event_name = 'claude_code.user_prompt') AS prompts,
       countIf(event_name = 'claude_code.tool_result') AS tool_calls,
       min(toDate(timestamp)) AS first_day, max(toDate(timestamp)) AS last_day
FROM clawd.events_raw FINAL WHERE provenance = 'legacy'
GROUP BY user_id FORMAT PrettyCompact
SQL

ch <<'SQL'
SELECT user_id,
       toUInt64(sumIf(value, metric_name = 'claude_code.token.usage')) AS tokens,
       round(sumIf(value, metric_name = 'claude_code.cost.usage'), 2) AS cost_usd,
       toUInt64(sumIf(value, metric_name = 'claude_code.commit.count')) AS commits,
       toUInt64(sumIf(value, metric_name = 'claude_code.session.count')) AS sessions
FROM clawd.metrics_raw FINAL WHERE provenance = 'legacy'
GROUP BY user_id FORMAT PrettyCompact
SQL
```

Compare against SQLite for the same window (bun:sqlite — no `sqlite3` CLI in
the image):

```bash
ssh clawdgg "docker compose -f $COMPOSE exec -T app bun -e '
  const { Database } = require(\"bun:sqlite\");
  const db = new Database(process.env.DATABASE_PATH ?? \"/data/clawd.db\", { readonly: true });
  console.table(db.query(\`
    SELECT d.user_id, count(*) AS days, sum(d.prompt_count) AS prompts,
           sum(d.tool_call_count) AS tool_calls,
           sum(d.input_tokens + d.output_tokens + d.cache_read_tokens + d.cache_creation_tokens) AS tokens,
           sum(d.cost_usd_cents)/100.0 AS cost_usd, sum(d.session_count) AS sessions
    FROM daily_stats d LEFT JOIN users u ON u.id = d.user_id
    WHERE u.otel_setup_date IS NULL OR d.date < u.otel_setup_date
    GROUP BY d.user_id\`).all());
'"
```

The columns must match **except** where the dry run reported skipped days —
those are intentionally absent from ClickHouse. To make that comparison a number
rather than an eyeball, add the dates the dry run named to the SQLite query:

```sql
    AND NOT (d.user_id = 'github_<id>' AND d.date = '2025-11-20')   -- one per skipped day
```

With those excluded the two sides must agree exactly, column for column. In the
rehearsal the user with no skipped days matched on the nose (9 days, 126
prompts, 223 tool calls, 5,425,073 tokens, $42.67, 35 sessions) and the other
two differed by precisely their skipped day.

**The idempotency check is the ROW COUNTS, not the dry run's day count.** An
earlier version of this step said a re-run "must report `0 new days`". It never
will, and that is by design, not a bug: `daysCoveredByOtherSources()`
deliberately ignores `provenance = 'legacy'`, because re-importing a legacy day
is a no-op by construction while importing over a day that live OTEL or a
backfill covers is a double count. So the dry run reports the same day count
forever — measured: 23 days before `--apply` and 23 days after it — and an
operator who believed that line would keep re-running `--apply` looking for a
zero that cannot arrive.

What must not move is what is actually in ClickHouse:

```bash
ch <<'SQL'
USE clawd;
SELECT * FROM (
  SELECT 'legacy metric rows' AS k, toUInt64(count()) AS v FROM metrics_raw FINAL WHERE provenance = 'legacy'
  UNION ALL SELECT 'legacy event rows', toUInt64(count()) FROM events_raw FINAL WHERE provenance = 'legacy'
  UNION ALL SELECT 'legacy tokens', toUInt64(sumIf(value, metric_name = 'claude_code.token.usage')) FROM metrics_raw FINAL WHERE provenance = 'legacy'
  UNION ALL SELECT 'legacy cost cents', toUInt64(sumIf(value, metric_name = 'claude_code.cost.usage') * 100) FROM metrics_raw FINAL WHERE provenance = 'legacy'
) ORDER BY k FORMAT PrettyCompact
SQL
```

Run that, run `--apply` a second time, run it again: the four numbers must be
identical. Verified in the rehearsal — 181 metric rows, 873 event rows,
12,511,226 tokens, 9,848 cents, unchanged across two applies. That is also the
repair procedure: a partially failed import is fixed by running `--apply` again,
because every row's identity is deterministic.

## 6. Rebuild the token and cost metrics that were already collapsed

`2026-10-19_repair_token_metrics.ts`. **After step 4, never before.**

This is the step that puts the lost tokens back. Steps 1–4 stop the collapsing;
they do not recover what was already merged away — but the measurement is not
actually gone. It is in `events_raw`, where every `api_request` row carries all
four token counters, the model, and Claude Code's own `cost_usd`, for the
single request it describes.

### Why there is anything to recover

Metrics are exported PERIODICALLY: every datapoint in one export interval shares
the export timestamp and differs only by model / query_source / speed, none of
which were in the old metrics key. So an interval covering ten requests
collapsed to one row per token type. Events are log records that carry the
instant they happened, so two of them collide only inside the same millisecond.

Prod, measured 2026-10-18, provenance='live', last 30 days:

| source | tokens |
|---|---|
| `sum(value)` of `claude_code.token.usage` (metrics_raw FINAL) | 9,446,112,211 |
| `sum(input+output+cacheRead+cacheWrite)` of `api_request` (events_raw FINAL) | 25,259,653,024 |

**63% of the tokens were missing**, and `claude_code.cost.usage` collapsed the
same way, so every dollar figure on the site is understated by roughly the same
share. Row counts say it from the other side: 1,477,211 events against 564,972
metrics, where one request should leave one event and four or five metric rows.

### BEFORE: confirm the diagnosis on your own data

Do not run the repair on faith. If metric rows share far fewer timestamps than
there are requests, the export-interval explanation holds. **If `instants` is
close to `requests`, it does not — stop and find the real cause.**

### The cutover, which is mandatory

`--before <cutover>` is **the step-4 EXCHANGE instant**, in UTC. Write it down
next to `$WATERMARK` when you run step 4, the same way, and pass the identical
value on every run of this script. It refuses to start without one.

If you did not write it down, recover it from the SERVER'S OWN LOG of the
statement — `system.query_log` holds every query it ran, the `EXCHANGE TABLES`
pair among them:

**`SYSTEM FLUSH LOGS` first, and it is not a formality.** `system.query_log` is
written asynchronously (7.5 s by default), so a read taken minutes after step 4
can simply not contain it yet — and if an earlier exchange IS in there, the
query below then answers with that one and looks entirely healthy. Measured: in
the rehearsal the read came back with an exchange 13 minutes stale, two
statements, verdict `PLAUSIBLE`. Flushing first makes the absence visible
instead.

```bash
# What ran, and when. Two statements are expected: metrics first, then events.
ch <<'SQL'
SYSTEM FLUSH LOGS;
SELECT toString(event_time) AS at, query_kind, substring(query, 1, 60) AS statement
FROM system.query_log
WHERE type = 'QueryFinish'
  AND query LIKE 'EXCHANGE TABLES%'
  AND event_time > now() - INTERVAL 60 DAY
ORDER BY event_time
FORMAT PrettyCompact
SQL
```

Then the value, with a check that refuses an implausible one rather than
handing you a number to paste:

```bash
ch <<'SQL'
SYSTEM FLUSH LOGS;
WITH
  seen AS (
    SELECT event_time FROM system.query_log
    WHERE type = 'QueryFinish'
      AND query LIKE 'EXCHANGE TABLES%'
      AND event_time > now() - INTERVAL 60 DAY
  ),
  latest AS (
    SELECT min(event_time) AS first_at, max(event_time) AS last_at, count() AS pair
    FROM seen WHERE event_time >= (SELECT max(event_time) FROM seen) - INTERVAL 5 MINUTE
  )
SELECT toString(first_at) AS cutover,
       pair AS statements_in_the_latest_exchange,
       (SELECT count() FROM seen) AS statements_in_60d,
       multiIf((SELECT count() FROM seen) = 0,
                 'REFUSE: no EXCHANGE in query_log. Logging off, rotated past it, or not yet flushed — flush and look again, then fall back to your own notes.',
               pair != 2,
                 'REFUSE: the latest EXCHANGE is not a pair of statements. Read the listing above and decide by hand.',
               first_at > now(),
                 'REFUSE: in the future — the server clock moved.',
               last_at - first_at > 3600,
                 'REFUSE: the two statements are more than an hour apart.',
               (SELECT count() FROM seen) > 2,
                 'PLAUSIBLE, BUT these tables have been exchanged more than once (see statements_in_60d). This is the MOST RECENT pair, which is the right cutover only if the earlier ones were a step-4 rollback. Check your notes before passing it.',
                 'PLAUSIBLE: pass this as --before') AS verdict
FROM latest
FORMAT Vertical
SQL
CUTOVER='2026-10-19 09:14:00'
```

**It anchors on the MOST RECENT exchange, not on `min()` over 60 days**, which
is what the previous version did. A step-4 rollback and a re-exchange leave four
statements in the log, and a global `min()` then hands you the first — the
rollback rehearsal, not the cutover — while refusing only on zero. Measured in
the rehearsal: with two exchanges 13 minutes apart, the old form answered with
the earlier one; this one answers with the later one, reports both counts, and
says out loud that the table was exchanged more than once so the operator
checks their notes rather than pasting a number.

An earlier cutover is the SAFE direction (it leaves a band unrepaired, visible
in the per-day diff) — the rehearsal confirmed that too, repairing 67.7B instead
of 68.2B tokens off a 13-minute-stale value, with no double count. A LATER one
supersedes exact rows, which is why the refusals above are refusals.

**The EARLIEST of the two**, which is the metrics exchange, because that is the
table step 6 rewrites — and because an earlier cutover is the safe direction
(see below). `system.query_log` is a system table with a TTL of its own, so
this stops working eventually: that is why the instruction is to write the
value down at step 4.

> **Do not use `min(timestamp)` of the new table for this.** The previous
> version of this runbook did, and it is wrong by months: after the EXCHANGE,
> `metrics_raw` holds the whole COPY, every row of which has a `row_id` and
> `provenance = 'live'` — so that query answers with the oldest live row there
> has ever been, not with the exchange. Passing it as `--before` would put the
> boundary before all of the history and repair nothing, which at least fails
> visibly; a cutover read off the wrong instant in the other direction
> supersedes exact rows.

Everything about step 6 is bounded by it:

- **Rows at or after it are exact.** They were written through the new sorting
  key, so they never collapsed, and rebuilding them from the events would
  DOUBLE them. Both the DELETE and the derive stop at the cutover.
- **It is what makes the step re-runnable while the app is up.** Live rows keep
  arriving throughout; without a fixed upper bound a second run an hour later
  would sweep an hour of exact rows into the repair.

A cutover **later** than the real exchange supersedes exact rows. An **earlier**
one leaves a band of collapsed rows unrepaired, which is harmless, visible in
the per-day diff, and fixed by re-running with the right one.

**Run it away from 00:00 UTC**, and not within a few minutes of it. The unit of
repair is a (user, UTC day) pair and the mutation takes minutes, so a run that
straddles midnight puts the day boundary in the middle of its own work.

### Run it

Dry run first. It changes nothing and prints, in order: the preflight, the
diagnosis, the collisions still visible in `events_raw`, any (user, day) pair
that holds both events and *reconstructed* metrics, the per-user before/after
with every refused pair named, and the cutover-edge exposure.

```bash
COMPOSE=/opt/clawdgg/docker-compose.staging.yml
ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE run --rm --no-deps \
  -v ./docker:/app/docker app \
  bun docker/clickhouse/migrations/2026-10-19_repair_token_metrics.ts --before '$CUTOVER'"

ssh clawdgg "cd /opt/clawdgg && docker compose -f $COMPOSE run --rm --no-deps \
  -v ./docker:/app/docker app \
  bun docker/clickhouse/migrations/2026-10-19_repair_token_metrics.ts --before '$CUTOVER' --apply"
```

It refuses outright, before touching anything, if:

| refusal | why |
|---|---|
| `--before` missing or unparseable | see above — it is the whole safety boundary |
| either sorting key does not end in `row_id` | step 4 is not done; the repair would be collapsed away |
| `metrics_raw` lacks a column the derive writes | the INSERT would fail *after* the DELETE |
| the derive SELECT does not run | same, and this one RUNS it rather than parsing it |
| a source event has `row_id = ''` | its derived rows would collapse into each other |
| a (user, day) pair holds both events and `backfill`/`legacy`/`import` token metrics | the DELETE only removes `live` rows, so that day would count the same history twice. Pass `--allow-mixed-days` to proceed having read the list |

`--apply` then, in this order: copies the rows it is about to delete into
`metrics_raw_pre_repair`, DELETEs them, INSERTs the derived rows, and re-reads
the per-user totals against the figures it printed first. The delete-then-insert
order is deliberate — a crash between them leaves the tokens briefly MISSING,
which is visible and fixed by re-running, rather than DOUBLED, which is not.

**What it will not supersede.** A (user, day) pair is repaired only when its
`api_request` events hold at least as many tokens AND at least as much cost as
its live metric rows do. A pair that fails that is printed as `NOT superseded`
with both sides, and keeps its original rows: the repair may not take away a
measurement it cannot match. A day with metric rows and no events at all is
left completely alone for the same reason.

**The one boundary it cannot fix.** Metrics lag their requests by up to one
export interval, so a datapoint covering a 23:59:50 request can be stamped
00:00:05 the next day, and one covering a request just before the cutover can be
stamped just after it. Where the neighbouring day or side of the cutover is not
itself superseded, that lagged datapoint survives while its request is also
rebuilt — a double count bounded by one export interval of one user's traffic,
at two edges: the midnight after a user's last active day, and the cutover
instant. The script prints the size of the second. Neither is repairable from
here, and both are far below the 63% being recovered.

## Known limits after all six steps

- **Collapsed TOKEN and COST rows are recoverable; nothing else is.** Step 6
  rebuilds them from the `api_request` events that measured the same requests.
  Everything else the old metrics key collapsed — lines of code, commits, PRs,
  active time, session counts — has no per-event twin and stays collapsed.
- **Even the repaired figure is "at least".** events_raw's old key ended in
  `timestamp` too, and `session_id` is empty on every live row, so two
  api_requests in the same millisecond collapsed there as well. **How much is
  not knowable** — a collapsed row leaves no trace of what it absorbed, and no
  query run afterwards can count rows that no longer exist. The script prints
  collisions that are still VISIBLE (api_request rows awaiting their merge, and
  surviving rows that share a millisecond with another). Those say the collisions
  keep happening; neither is a bound on what already went. Publish the repaired
  totals as "at least", not as exact, and do not quote either figure as a floor
  on the loss.
- **`session_id` is empty on 100% of live rows, and `decision` on 100% of
  tool_results** (71,478 of 71,478 over 7 days, measured 2026-10-18). Both are
  fixed in the app going forward; the historical rows stay empty, so
  per-session analytics and tool decision-source figures only start from the
  step-2 deploy. The read paths already exclude `session_id = ''`.
- **Legacy days have no detail.** The import reconstructs counts and sums, not
  events: `prompt_length` is 0, `model` and `session_id` are empty, and every
  row sits at 12:00 UTC. The read paths compensate — `provenance='legacy'` is
  excluded from hour-of-day and heatmap queries, `session_id = ''` from
  per-session analytics, `model = ''` from cache-savings, and the daily
  `sessions` figure comes from the `claude_code.session.count` metric rather
  than `uniqExact(session_id)`.
- **`tool_success` is not real on legacy rows.** daily_stats counted tool
  calls, not outcomes, so legacy rows are excluded from success-rate queries
  rather than being reported as 100% successful.
- **Haiku 5.5 long prompts and Opus fast mode are priced only where the input
  says so.** Both are now in `src/lib/pricing.ts`, and the JSONL import reads
  `message.usage.speed` and the request's own token counts. Live OTLP rows
  carry Claude Code's own measured cost and need neither. The ClickHouse
  cache-savings estimate applies fast mode (the rows carry `speed`) but cannot
  apply Haiku's prompt-length tier, which is decided per request.
- **`agent_id` / `parent_agent_id` and a 5m/1h cache-creation split are not
  captured** because the current docs do not define them. Subagent attribution
  is `query_source` + `agent.name`; `api_request` reports one
  `cache_creation_tokens` with no TTL breakdown.
- **`attempt`, `tool_input_size_bytes`, `tool_result_size_bytes`,
  `app.entrypoint`, `ccr.session.id`, `user.id` and `user.email` are not
  stored.** They are emitted, but none can distinguish two records sharing a
  timestamp and a session, and `user.email` is PII with no use here.
